# SRC per-run non-determinism from `Index::id()`-based ordering (fixed, two sites; one residual cause open)

## Summary

`gw-rs` (a downstream consumer of this crate's TreeTN/SRC contraction) has a
long-standing "Known issues" entry describing run-to-run non-determinism at
fixed R/T/MU/U and fixed RNG seeds -- wall time and converged ACI bond
dimension both vary widely across repeated runs of the identical pipeline,
and the entry notes this survives pinning `RAYON_NUM_THREADS`/OMP/VECLIB/
OPENBLAS/MKL to 1. Investigating that report (via gw-rs's own
`determinism_probe.rs`, and by exercising this crate's `contract_src`
directly) traced two concrete, fixed root causes in
`crates/tensor4all-treetn/src/treetn/contraction/{src_probe,src_tree}.rs`,
plus a third, smaller-magnitude, still-open source in a different layer (see
"Residual, not fixed" below).

## Root cause (both fixed sites)

`tensor4all_core::sort_indices_deterministic` sorts by `(dim, plev, id,
Debug)`. Its name notwithstanding, this is only a *stable* order given an
already-materialized index list within one process -- the `id` tie-break is
`Index::id()`, generated by `generate_id()`
(`tensor4all-core/src/defaults/index.rs`), which draws from a thread-local,
OS-entropy-seeded `rand::rngs::ThreadRng`, not from any caller-supplied seed.
Minimal proof: sorting ten freshly-created, same-dimension `DynIndex`s with
this function, in the same process, gives a different creation-order ->
sorted-position permutation on every run:

```
[7, 3, 8, 0, 2, 5, 4, 9, 1, 6]
[6, 9, 1, 5, 8, 7, 4, 2, 3, 0]
[6, 1, 0, 4, 3, 5, 2, 7, 9, 8]
```

Two call sites in the SRC path fed this random tie-break directly into
numerically-consequential ordering:

1. **`src_probe.rs::local_output_indices`** built the returned output-index
   list via `HashSet` set-difference (`a_external.difference(&b_external)`,
   iteration order itself is hash-order) and then
   `sort_indices_deterministic`, discarding the tensor's own
   construction-order `external_indices()`. This list is consumed
   sequentially by `ProbeBank::extend_to`, which draws Gaussian sketch
   values from a *correctly* seeded `StdRng` in the list's order -- so when
   a node has two or more same-dimension physical output legs (common: many
   sites share a local Hilbert-space dimension), *which* leg received
   *which* seeded Gaussian column was random per process, even with a fixed
   SRC seed.

2. **`src_tree.rs`'s top-level `probe_indices`** (general rooted-tree path)
   was flattened via `outputs.values()` (a `HashMap<V, Vec<Index>>`) instead
   of walking the already-sorted `nodes: Vec<V>` -- `HashMap` iteration
   order is itself randomized per process, independent of any `Index::id()`
   ties, so this reshuffled *whole per-node blocks* of the same
   seeded-RNG-consumption order across runs.

3. **`src_tree.rs::uncontracted_indices`** (used to build the row index list
   fed to each edge's QR factorization) had the identical
   `HashMap`-count-then-`sort_indices_deterministic` shape. Unlike (1)/(2),
   a QR row permutation does not change the mathematical result (only which
   row of `Q` a given index labels) -- but `contract()` re-mints every bond
   index's random id on *every call* (`sim_internal_inds()`), so this tie
   reshuffled the row order (and therefore the QR routine's floating-point
   rounding) *per call*, not just per process. Confirmed via a direct probe:
   with (1) and (2) fixed but (3) still buggy, three back-to-back calls to
   `contract()` on the exact same in-memory input tensors, same seed,
   *within one process*, already disagreed at the ~13th significant digit.

## Fix

All three sites now derive order from data that is stable across both
process restarts and repeated calls: each tensor's own fixed
`external_indices()` order (1), the already-sorted `nodes` list (2), and
each `factors` argument's own given order plus each factor's own index
order, first-occurrence deduplicated (3). None of them call
`sort_indices_deterministic` any more. `generate_id()`/`Index::id()`
themselves are untouched -- randomized ids remain necessary for the
ITensors.jl-style identity/uniqueness guarantee across independently
constructed networks; the fix only removes them as an *ordering* signal
where ties are structurally possible.

Regression tests (`local_output_indices_orders_same_dimension_legs_by_construction_not_by_random_id`
in `src_probe.rs`, `uncontracted_indices_orders_same_dimension_survivors_by_factor_order_not_random_id`
in `src_tree.rs`) rebuild same-dimension indices fresh on every one of 200
loop iterations and assert a fixed expected order every time. Verified by
temporarily reverting each fix in isolation: both tests then fail reliably
(a coin-flip per iteration means a 200-iteration run passing by chance has
probability `2^-200`).

## Residual, not fixed: a third, smaller-magnitude source

After both fixes above, `src_tree.rs`/`src_probe.rs`/`src_chain.rs` contain
no remaining `sort_indices_deterministic` calls, yet a direct probe (fixed
seed, fixed in-memory input tensors, hub/star topology, `contract_src`
fixed-rank) still shows non-bit-identical dense output:

- **Across separate process runs**: relative differences of order `1e-12`
  (e.g. `sum=2.97260830949495949e3` vs `2.97260830949494857e3`).
- **Within one process**, across three back-to-back calls to `contract()` on
  the same input tensors and same seed: the same `~1e-12`-relative
  disagreement is already present.
- Unaffected by pinning `RAYON_NUM_THREADS`/`OMP_NUM_THREADS`/
  `OPENBLAS_NUM_THREADS` to 1 -- consistent with gw-rs's own report about
  the pre-SRC pipeline.

Magnitude (`~1e-12` relative) is consistent with floating-point
non-associativity (a different but mathematically equivalent operation
order somewhere in the GEMM/QR/einsum stack), not with another
misdirected-sketch-assignment bug of the (1)/(2) kind, which would produce
an O(1) relative difference. Since this class of bug has now been fully
removed from the `sort_indices_deterministic` pattern in the SRC module
itself, the next investigative step is the backend layer (`factorize_full_rank`,
`tensor4all-tensorbackend`'s QR/GEMM implementation, or `T::contract`'s
generic einsum path), not another index-ordering search in this module.
Not pursued further in this pass -- tracked here for whoever picks this up
next.

## Provenance

The paper (Camaño--Epperly--Tropp, arXiv:2504.06475) and its reference
Python implementation (`chriscamano/RandomMPOMPS`) enumerate sites by plain
list position and have no analog of "index identity via a random tag" at
all, so this bug class does not exist in the reference implementation and
neither source specifies how to fix it. They do, indirectly, confirm the
right invariant to restore: the canonical order for a site's physical legs
or a node's uncontracted indices is the *structural* position (site index /
node order), not any property of the index's own (here, randomized)
identity -- which is exactly what both fixes above restore.
